# 全局行为准则（RULES）

> 适用于所有任务的全局约定，与任务模板分工：模板管"这一次任务"，本文件管"所有任务"。
> **用法**：放在项目根目录，或并入项目的 CLAUDE.md / AGENTS.md。

## 1. 方案取向

- 实现功能前，先查阅开源社区与官方文档的既有最佳实践；存在则优先复用，或深度利用其核心实现
- 不盲目套用，也不闭门造车——完全不看参考是禁区
- 从本地真实需求出发，不设过于苛刻的条件；开发期间适当放宽验收标准，有助于项目推进

## 2. 代码理解与风格

- 动手编辑前，把相关源码完整读两遍
- 模仿既有代码的命名风格和格式
- 在关键步骤添加注释；若项目带有学习目的，复杂逻辑的注释应面向学习者书写
- 新文件命名遵循事先声明的模式（如 `{{model}}*.py` / `*.{{model}}.py`）；命名禁用难懂缩写，必要时配套一份变量说明文档

## 3. 范围纪律（上下文保护）

- 只读、只动授权清单内的文件与目录；清单外默认视为无关或缓存
- 明令禁止触碰的内容（缓存、已污染的数据）一律不动
- 新产物隔离：放入专用文件夹或遵循声明的命名模式，不污染原有目录

## 4. 质量门禁

- 交付前必须运行任务书给出的验证命令，且正常结束；"应该可以"不算通过
- 验证以日志与输出为证据，不以直觉为证据

## 5. 交付规范

- 分析 / 报告 / 方案类产出统一放 `docs/`；写明字数上限与语言
- 长任务输出重定向到 log 文件，供事后 review
- 多阶段任务显式声明依赖顺序：前置任务未完成不得开始

## 6. 沟通与忠实性

- 不曲解、不私自篡改用户观点；不改动或编造理论、数据与引用
- 返工时先对照"期望流程"逐条自查，再汇报

# Working core rules

**"不要默认假设。不要隐藏困惑。呈现权衡。"**
**每个人的想法都受限于认知，注意提醒用户的Unknown unknown。**

## 1. 先思考再编码

实现之前：

- 明确陈述假设；如果不确定或不明白，就提问。不要擅自为用户做决定。
- 当存在多种理解时，逐一列出而非默默选择。
- 如果存在更简单的方案，直接说明并在必要时提出异议。

## 2. 简洁优先

**"用最少的代码解决问题。不做臆测性编码。"**

- 不实现超出需求的特性。
- 不为仅使用一次的代码做抽象。
- 不添加未经要求的"灵活性"或"可配置性"。
- **不处理在当前系统边界内不会发生的错误场景。**

## 3. 精准改动

**"只改必须改的。只清理自己制造的遗留。"**

编辑现有代码时：

- 不要"改善"相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- **与现有风格保持一致。**
- 如果发现无关的废弃代码，提出来而不是直接删除。

当你的改动产生了孤立的代码时：

- 移除因你的改动而变得未使用的 import/变量/函数。
- 不要移除之前就存在的废弃代码，除非被明确要求。

检验标准："每一行改动都应该能追溯到用户的请求。"

## 4. 代码提交

- commit信息始终遵循社区主流规范，不添加“第一轮”“批次”等无效工作计划信息
- 每次commit的代码应该服务于同一个主题，目的或者任务，不要将多个关联不大的改动一起提交
- 如果工作区出现了其他你没有参与改动的代码，除非用户要求，不要擅自修改或者commit对方的改动

## 5. 文档维护与注释

- 不要写无意义的废话注释
- 不要写将代码重新解释一遍的注释，代码本身就能够解释
- 不要写代码工作的原理，而应该写
  - 这个模块设计的理念，它在整个架构实现中的定位，它服务于/连接了/解决了什么
  - MagicNumber的取舍，为什么会出现硬编码的MagicNumber
- 保持代码简洁，用词精准，消除语义潜在的歧义

- 非必要不要每次修改文件时都写注释，代码本身就是解释，除非是必须考虑的失败案例
- 前端UI设计中不要自主加上MagicNumber，如果有，比如向用户报告

## 6. 视觉检测

- 对于设计到动画效果而不是静态固定页面的检测，禁止使用 playwright, 禁止自己写探针脚本来截取动画多帧，应该让用户自己审阅动画效果

## 4. 从用户体验出发设计UX

- 用贴切的图标/ICON代替文字，减少认知负担
- 学习优秀软件的设计，比如Apple，ChatGPT网页版
- 存在动画时，维持视线的稳定移动
  - 若一个元素一直存在，尽量不要出现移动方向之外的位移变化
  - 若一个元素在动画前后存在状态发生改变，尽量不要影响其他元素的位移

## 5. subagents

- 当你需要开启subaget并且提交给subagents的任务是多个重复类型的任务时，考虑增加subagent的数量并行执行提高速度
- 记住，你最多同时开始5个subagents，控制好你的并发数
